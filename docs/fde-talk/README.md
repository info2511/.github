## 二、核心发现（按重要性排序）

### 1. 案例最强的证据不是效率数字，是那个意外发现（08 页）

页脚紫色重音：**「还发现人工『容忍区间』内未继续追查的账款差异。」**

人工流程存在隐性放弃阈值——差异小到不值得追就不追。AI 没有这个阈值，于是捞回了组织原本系统性放弃的价值。这是效率叙事之外的**第二类收益**，且是任何供应商都编不出来的——只有真做过才知道人工流程里有这么个区间。

与之相对，同页的效率数字反而是全篇最弱的证据：`1–2 人天 / 结算周期` → `数小时`，但 AFTER 的附注是「店长只处理异常」——**比的不是同一件事的耗时，是重构后剩余人工的耗时**。「数小时」也无精确口径。见第四节问题 2。

### 2. 双账本才是 FDE 的商业模式本体（05 页）

| 客户价值账 | 产品资产账 |
|---|---|
| 指标改善 | 行业方法 |
| 真实使用 | 复用组件 |
| 离场后可继续 | 下次更快更稳 |

同一次交付同时产出客户侧结果和供方侧资产。这是「不是驻场外包」的实质——**外包只记第一本账，FDE 两本都记**。

### 3. 同心圆的拓扑是刻意的：人在技术外面（08 页）

`CORE` 业务结果 ← `MIDDLE` 技术（OCR、结构化、比对、异常证据）← `OUTER` 人的判断（店长判断、追账+沟通+确认）← `FEEDBACK` 回流。

技术夹在业务结果与人的判断之间，**人是最外层的包裹而非被包裹者**。与 06 页四个场景（资料与证据／线索与建议／抽取与比对／候选与错误）的「候选生成 + 人工复核」逻辑严格一致，也与 03 页「不能承担高风险责任」一脉相承。这不是画图习惯，是方法论的空间表达。

### 4. 两条六阶段轴的错位（02 vs 04 页）

| # | Slide 02 · 能力供给侧 | Slide 04 · 企业落地侧 | 对位 |
|---|---|---|---|
| 01 | Chat（对话与生成） | 模型回答 | ✅ 严格对应 |
| 02 | Agent + MCP（行动力与接口） | 完成一次任务 | ✅ 严格对应 |
| 03 | Skill（岗位手册） | 真实数据持续进入 | ⚠️ 方法沉淀 vs 数据工程 |
| 04 | Harness（工作环境与护栏） | 流程 / 权限 / 复核 | ✅ 语义对应 |
| 05 | Loop（反馈与管理闭环） | 一线持续采用 | ❌ 技术闭环 vs 人的行为改变 |
| 06 | Multi-Agent（协作网络） | 业务指标改变 | ❌ 技术形态 vs 业务结果 |

**这个错位就是演讲的论点本身**：技术轴到 06 不会自动把落地轴推到 06。脱钩的两格正是 03 页右栏「不会自动改变员工习惯」「不知道经营优先级」所指。

### 5. 07 页第 04 条越入 HR 层面，slide 未展开

> 「流程、权限、岗位、评价都不动，AI 就只是额外工作。」

把 03 页「不会自动改变员工习惯」和 04 页死法 01 收敛成一个可执行的前置条件——**动 AI 之前先动岗位与评价**。这已经出了 IT 范围。谁来动、怎么动、动之前如何与员工沟通，七页中无一处交代。紧邻它的紫色句「效率释放以后，人做什么？要在自动化之前设计」把问题点了出来，同样悬置。

### 6. 07 与 08 是配套的两页，应连读

07 页给角色，08 页给这些角色各自要回答的问题：

| 07 页 · 最小单元五角色 | 08 页 · 五个组织问题 |
|---|---|
| IT / 数据 | 谁持续供数 |
| 业务背结果 | 谁确认口径 |
| 一号位定方向 | 什么算异常 |
| 一线守边界 | 谁处理异常 |
| 一线 + FDE 搭闭环 | 失效时如何回退人工 |

| 预测（批次） | 结果 |

**关于第四种死法**：它没有以死法卡的形式出现在 04 页，而是以**否定式规则**散在 07 页页脚的四条里：

| 07 页四条否定 | 对应的运营期失败模式 |
|---|---|
| 不先考核 Token | 考核了错的东西（04 页死法 03 的具体化） |
| 不把 AI 负责人做成代操作服务台 | 责任错位：AI 负责人代劳，业务工作方式不变 |
| 业务不能只提需求 | 业务方不投入 |
| **FDE 离场必须有人接手** | **离场后断档——即第一批追问的第四种死法** |

第四种死法**以规则形式补上了，但仍无死法卡、无根因分析**。04 页的乘法公式里 `持续迭代` 那一格，至今没有配一个「这样会死」的场景。

## 四、三个未答问题的当前状态

### 问题 1 · 知识资产归属 —— 仍完全未答，且被案例加强 🔴

05 页第 02 步是「把专家的隐性知识变成规则与例外」，产品资产账里是「行业方法｜复用组件」。08 页案例把这件事做实了：**「什么算异常」的判定口径是客户的业务知识，被固化进系统之后归谁？** 案例讲了口径如何确认，没讲口径归谁所有、能否跨客户复用、脱敏边界在哪。七页无一字提及。

这同时是商业条款问题和数据治理问题，也是本篇最该当面追问的一条。案例讲得越具体，这个空白越显眼。

### 问题 2 · 从判断窗口到「指标改变」的空白 —— 部分回答 🟡

07 页把 06 页的「两到四周」细化成两个检查点：**「两周看什么、三十天看什么」**。但注意两点：

- **口径轻微不一致**：06 页说 2–4 周（14–28 天），07 页的第二个检查点是 30 天，超出上限。是同一套 gate 的两种表述还是两版口径，可追问。
- **从 30 天到 04 页合格线「业务指标改变」之间仍是空白**：08 页案例给了 before/after，但没给达成时间线——多久做到「数小时」的，slide 未说。

### 问题 3 · 客户侧的迭代机制 —— 部分回答 🟡

三处新增：07 页「FDE 离场必须有人接手」、07 页五角色最小单元、08 页「误报／漏报／新规则持续回流」。**机制的形状有了**——回流通道存在，接手的人必须存在。

**仍未答的是谁维持它**：回流通道的运营责任落在五角色的哪一个？接手的人靠什么保证半年后回流没有停？08 页的 FEEDBACK 层画了箭头，没写责任人。

## 五、可挑战点（均非原文表述）

1. **BEFORE / AFTER 口径不对等**（08 页）：`1–2 人天` → `数小时` 比的不是同一件事，AFTER 已经是重构后的剩余人工。加上「数小时」无精确口径，这组数字不构成可审计的指标改善。同页的「容忍区间」发现反而更有说服力。
2. **证据与自我定位不自洽**（02 页）：轴上标「当前 = 04 Harness」，但自己举的三条证据分别落在阶段 04、03、06。
3. **`5 CONDITIONS · 3 GROUPS` 标签与内容对不上**（06 页）：三条各含两个要素，实际是 6 个要素分 3 组。
4. **判断窗口两版口径**（06 页 2–4 周 vs 07 页两周／三十天）：30 天超出 28 天上限。
5. **右栏七项不是同一类否定**（03 页）：可拆为**认知缺失**、**工程不可靠**、**制度不可授权**三层，前两层可工程化缓解，第三层只能由组织设计承担。平铺一栏掩盖了「哪些能靠 FDE 解决、哪些不能」。
6. **方法论对「组织本身有病」的客户无解**（03 + 05 + 06 + 07 交叉）：03 页说 AI 不能解决部门权责冲突；05 页说 FDE「不是替业务拍板」；06 页把「没有业务负责人」列为 NO-GO；07 页要求一号位亲自任命真正负责人。四条合起来自洽，但结论是——**权责冲突到找不出负责人的组织，FDE 直接不接**。这是清晰的适用边界，但从未明说，容易被听成「FDE 能解决组织问题」。
7. **死法卡排序是时间顺序而非严重度**（04 页）：采购期 → 试点期 → 运营期，三种死法可连续发生在同一客户身上，不是三选一。
