## 二、核心发现（按重要性排序）

### 1. 双账本才是 FDE 的商业模式本体（Slide 05）

05 页页脚两本账并列，是全篇唯一一次披露交付的收益结构：

| 客户价值账 | 产品资产账 |
|---|---|
| 指标改善 | 行业方法 |
| 真实使用 | 复用组件 |
| 离场后可继续 | 下次更快更稳 |

同一次交付同时产出客户侧结果和供方侧资产。这是标题那句「不是驻场外包」的实质——**外包只记第一本账，FDE 两本都记**。所有关于 FDE 与外包/咨询有何不同的讨论，最后都落在这里。

### 2. 两条六阶段轴的错位（Slide 02 vs 04）

演讲在 02、04 页各给一条六格轴，视觉上刻意呼应，但后半段脱钩：

| # | Slide 02 · 能力供给侧 | Slide 04 · 企业落地侧 | 对位 |
|---|---|---|---|
| 01 | Chat（对话与生成） | 模型回答 | ✅ 严格对应 |
| 02 | Agent + MCP（行动力与接口） | 完成一次任务 | ✅ 严格对应 |
| 03 | Skill（岗位手册） | 真实数据持续进入 | ⚠️ Skill 是方法沉淀，落地轴 03 是数据工程 |
| 04 | Harness（工作环境与护栏） | 流程 / 权限 / 复核 | ✅ 语义对应 |
| 05 | Loop（反馈与管理闭环） | 一线持续采用 | ❌ 技术闭环 vs 人的行为改变 |
| 06 | Multi-Agent（协作网络） | 业务指标改变 | ❌ 技术形态 vs 业务结果 |

**这个错位就是演讲的论点本身**：技术轴到 06 不会自动把落地轴推到 06。脱钩的两格（一线持续采用、业务指标改变）正是 03 页右栏「不会自动改变员工习惯」「不知道经营优先级」所指。隐含 gap：技术侧在 04，企业侧多在 01–02——FDE 的存在理由。

### 3. 06 页是从「论述」转向「操作」的转折点

六条 `NO-GO SIGNALS` 把前三页的抽象结论翻译成可执行的筛客户清单，逐条可回指 03、04 页（对照表见 `slides.md` Slide 06 读图备注）。同时给出全篇**第一个演讲者自己的量化承诺**：`两到四周能否判断继续、调整或停止`。此前唯一的数字（02 页 `≈1M 行代码`）是引用他人。

### 4. 选品逻辑是刻意的：只做「候选生成 + 人工复核」

06 页底部四场景——医疗｜资料与证据、销售｜线索与建议、文档｜抽取与比对、研发｜候选与错误——共同结构是把最终判断留给人，没有一个是自动决策。与条件 03「首版保留人工判断」、NO-GO「首版就自动高风险决策」严格自洽，也与 03 页「不能承担高风险责任」一致。这不是举例随手，是方法论的边界声明。

## 四、三个仍未回答的问题（当面追问的优先级）

### 问题 1 · 知识资产归属（最高优先级）

05 页第 02 步是「把专家的隐性知识变成规则与例外」，产品资产账里是「行业方法｜复用组件」。合起来读：**客户的专家知识经 FDE 之手成为供方的可复用资产**。归属、脱敏边界、跨客户复用的限制，slide 全篇未提。对 AI 治理视角这是最该问的一条——它同时是商业条款问题和数据治理问题。

### 问题 2 · 从「2–4 周」到「指标改变」之间的空白

06 页承诺 2–4 周判断继续／调整／停止；04 页把合格线定在落地轴 06「业务指标改变」。两者之间的时间跨度和中间里程碑，五页中没有任何一页交代。注意 2–4 周判断的是**要不要继续**，不是**是否见效**——这两件事常被混为一谈，值得当面点破。

### 问题 3 · 客户侧的迭代机制仍然缺席

05 页的「沉淀」补上了 `持续迭代` 因子，但补的是**供方侧**（下次更快更稳）。客户侧对应的只有一句承诺式的「离场后可继续」，没有机制。第一批指出的第四种死法——上线后无迭代机制、半年内衰减——在 06 页被处理为**事前筛选**（NO-GO 挡掉不合格客户），而不是**事后维持**。合格客户在 FDE 离场后如何自己维持迭代，仍是空白。

## 五、可挑战点（均非原文表述）

1. **证据与自我定位不自洽**（02 页）：轴上标「当前 = 04 Harness」，但自己举的三条证据分别落在阶段 04、03、06。若 Claude Tag 已做到团队级交付（阶段 06），「当前在 04」低估了自己的论据。
2. **`5 CONDITIONS · 3 GROUPS` 标签与内容对不上**（06 页）：三条各含两个要素，实际是 6 个要素分 3 组，不是 5 个。改稿遗留还是原设计中有一对本属同一条件，可直接追问。
3. **右栏七项不是同一类否定**（03 页）：可拆为**认知缺失**（不理解公司／不知经营优先级）、**工程不可靠**（不能保证稳定／错误彼此传播）、**制度不可授权**（权责冲突／高风险责任／员工习惯）三层。前两层可工程化缓解，第三层只能由组织设计承担。平铺成一栏掩盖了「哪些能靠 FDE 解决、哪些不能」。
4. **方法论对「组织本身有病」的客户无解**（03 + 05 + 06 交叉）：03 页说 AI 不能解决部门权责冲突；05 页说 FDE「不是替业务拍板」；06 页把「没有业务负责人」列为 NO-GO。三条合起来是自洽的，但结论是——**权责冲突到找不出负责人的组织，FDE 直接不接**。这是清晰的适用边界，但 slide 从未明说，容易被听成「FDE 能解决组织问题」。
5. **死法卡的排序是时间顺序而非严重度**（04 页）：采购期 → 试点期 → 运营期，三种死法可以连续发生在同一客户身上，不是三选一。按「三选一」讲会低估累积失败率。
